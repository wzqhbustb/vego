# 为什么 LanceDB 使用页式存储而非 LSM Tree

> 向量数据库存储格式设计决策的技术分析

## 摘要

LanceDB（以及 Vego）采用**基于页的列式存储格式配合 Deletion Vector**，而非广泛使用的 LSM Tree 架构。本文解释这一决策背后的技术原理，比较 LSM Tree 与 Lance 方案在 AI/向量工作负载上的权衡。

---

## 1. 架构对比

| 维度 | LSM Tree | Lance 页式存储 |
|------|----------|----------------|
| **写入模式** | 高频随机写入 | 批量导向，追加为主 |
| **读取模式** | 点查 | 列式扫描、ANN 搜索、范围查询 |
| **数据布局** | 行式（SSTables） | 列式（Pages） |
| **更新策略** | 多版本 + 压缩 | 写时复制 + Deletion Vector |
| **压缩频率** | 频繁，前台/后台 | 低频，可调度 |
| **空间放大** | 1.1x - 3x | 可控（DV 压缩后） |
| **写放大** | 10x - 100x（压缩） | ~1x（追加 + DV 标记） |
| **读放大** | O(log N) 层级 | O(1) 直接页访问 |

---

## 2. 工作负载特征

### 2.1 LSM Tree：源于 OLTP，适配分析场景

LSM Tree 最初设计（O'Neil, 1996）是为了解决 B-Tree 在**写密集型 OLTP 负载**中的写放大问题。虽然现代变种（RocksDB、LevelDB）被用于一些分析系统，但其核心优化仍围绕 OLTP：

**原始设计目标（OLTP）**：
- 高吞吐随机键值写入（主要动机）
- 通过顺序 WAL + MemTable 实现低写入延迟
- 配合布隆过滤器的快速点查
- 小记录更新（通常 < 1KB）

**分析场景的适配**：
一些数据库（ClickHouse MergeTree、Druid、InfluxDB I/Ox）使用类 LSM 结构，但需要大量改造：
- LSM 之上的列式存储层（MergeTree）
- 专用压缩编解码器
- 时间范围分区（时序优化）

**核心洞察**：纯 LSM（RocksDB）是行式的，针对键值访问模式优化。将其用于列式分析需要增加架构层次，增加复杂性。

```
典型 LSM 流程：
写入 → WAL → MemTable → Immutable → Flush → L0 SSTable 
     → 压缩 → L1/L2/L3 SSTables
```

### 2.2 向量数据库：AI/分析型工作负载

向量数据库如 LanceDB 面临不同的挑战：
- **批量导入**：一次性导入数百万向量（如嵌入数据集）
- **近似搜索**：ANN 查询不需要精确点查
- **列式访问**：仅投影需要的维度进行过滤
- **追加为主**：更新较少；删除使用软删除模式

```
Lance 流程：
批量写入 → 列页 → Deletion Vector（用于更新）
     → 后台压缩（可调度，低频）
```

## 3. 向量数据的问题

### 3.1 尺寸至关重要

高维向量体积庞大：

| 维度 | Float32 大小 | 典型用例 |
|------|-------------|----------|
| 384 | 1.5 KB | 句子嵌入（all-MiniLM） |
| 768 | 3 KB | BERT 风格嵌入 |
| 1536 | 6 KB | OpenAI text-embedding-3-large |
| 1024×768（图像） | 3 MB | 视觉 Transformer 补丁 |

**LSM Tree 的挑战**：
- 频繁压缩重写 3KB-6KB 条目 = 巨大的 I/O 放大
- HNSW/IVF 索引与 SSTable 结构难以自然结合
- 大向量的多版本会迅速耗尽存储空间

**Lance 的解决方案**：
- 列式页：向量连续存储，利于 SIMD 效率
- Deletion Vector：位掩码标记删除行（字节级 vs 重写 GB 级数据）
- 不可变页：新数据追加到新页，旧页保持不变

### 3.2 ANN 索引集成

```go
// LSM + HNSW：配合不佳
// 每次压缩改变行 ID → 需要重建 HNSW

// Lance + HNSW：自然配合
// 页位置稳定 → HNSW 存储 (pageID, offset) 引用
// Deletion Vector 过滤结果而无需重建索引
```

## 4. 多模态存储需求

现代 AI 应用处理多样化的数据类型：

| 数据类型 | 大小 | 访问模式 | 存储策略 |
|----------|------|---------|----------|
| 嵌入向量 | KB | 随机访问（ANN） | 页内联存储 |
| 元数据 | B-KB | 过滤/扫描 | 列式页 |
| 图像 | 100KB-10MB | 懒加载 | Pack 文件 |
| 视频 | 10MB-1GB | 流式 | 独立 Blob 文件 |

### 4.1 Lance 的分层 Blob 存储

Lance 支持"**逻辑统一、物理分离**"的存储方式：

```go
// 三层 blob 存储（来自 Vego 路线图）
type BlobStorage interface {
    // 第一层：内联（< 64KB）- 直接存储在页中
    // 第二层：打包（64KB - 4MB）- 存储在 .pack 侧车文件
    // 第三层：独立（> 4MB）- 存储在单独的 .blob 文件
}

// 懒加载 API
func (c *Collection) TakeBlobs(column string, ids []string) ([]BlobFile, error)
```

**为什么 LSM 做不到**：
- SSTable 是自包含的；跨文件分割数据会破坏假设
- LSM 压缩期望原子性重写整个记录
- 不支持"先读元数据，懒加载 blob"的模式

## 5. 性能权衡

### 5.1 写入性能

| 场景 | LSM Tree | Lance |
|------|----------|-------|
| 顺序批量加载 | 良好 | 优秀 |
| 随机单条写入 | 优秀 | 良好 |
| 大值更新 | 差（高写放大） | 良好（DV 标记） |
| 向量更新 | 很差 | 良好 |

**写放大（WA）**：
- LSM：10-100x（重复压缩重写）
- Lance：~1x（追加 + 偶尔的 DV 压缩）

### 5.2 读取性能

| 查询类型 | LSM Tree | Lance |
|----------|----------|-------|
| 点查 | 优秀 | 良好 |
| 范围扫描 | 良好 | 优秀（列式） |
| 全表扫描 | 差 | 优秀（向量化） |
| ANN 搜索 | 差（需要额外索引） | 优秀（原生 HNSW/IVF） |
| 投影下推 | 不适用 | 优秀（只读需要的列） |

### 5.3 空间效率

```
LSM 空间放大公式：
SA = （所有版本大小） / （存活数据大小）
典型值：1.1x - 3x，取决于压缩策略

Lance 空间放大：
SA = （存活数据 + deletion vector + 未压缩页） / （存活数据）
典型值：1.0x - 1.3x（压缩回收 DV 标记空间）
```

## 6. Lance 的更新策略：写时复制 + Deletion Vector

### 6.1 Deletion Vector（DV）

一种位打包结构，标记逻辑删除的行：

```go
type DeletionVector interface {
    Contains(rowID uint32) bool    // O(1) 检查
    Set(rowID uint32)              // O(1) 标记删除
    Count() int                    // 删除计数
    Serialize() ([]byte, error)   // 持久化到 .del 文件
    Deserialize([]byte) error
}
```

### 6.2 更新流程

```
更新操作：
┌─────────────────────────────────────────────────────────┐
│ 1. 读取旧文档 → 获取 oldRowID                           │
│    （页位置稳定，无需更新索引）                          │
├─────────────────────────────────────────────────────────┤
│ 2. 在 DV 中标记 oldRowID 已删除                         │
│    （O(1) 位图操作，无需重写页）                        │
├─────────────────────────────────────────────────────────┤
│ 3. 追加新文档 → 获取 newRowID                           │
│    （追加到新页，更新 HNSW 新点）                        │
├─────────────────────────────────────────────────────────┤
│ 4. 搜索自动通过 DV 过滤                                 │
│    （HNSW 返回候选，通过 DV 位掩码过滤）                │
└─────────────────────────────────────────────────────────┘
```

### 6.3 压缩策略

与 LSM 的强制压缩不同：

| 触发条件 | LSM | Lance |
|---------|-----|-------|
| 频率 | 持续/层级制 | 可调度/按需 |
| 范围 | 整个层级 | 选中的片段 |
| I/O 模式 | 大量顺序读写 | 有针对性的页重写 |
| 用户影响 | 延迟峰值 | 后台，可限流 |

```
Lance 压缩：
- 触发：DV 删除比例 > 30%（可配置）
- 动作：重写页，排除已删除行
- 收益：回收空间而无需重建索引
```

## 7. 何时使用哪种方案？

### 澄清：RocksDB 是分析型引擎吗？

**RocksDB 本质上是 OLTP 引擎**，尽管它被用作多种系统的存储后端：

| 系统 | 用例 | LSM 角色 | 额外层次 |
|------|------|---------|----------|
| **MyRocks** (MySQL) | SQL OLTP | 存储引擎 | 上层 SQL 层 |
| **TiKV** | 分布式 OLTP | 键值存储 | TiDB SQL 层 |
| **MongoDB WiredTiger** | 文档 OLTP | 存储引擎 | 文档模型 |
| **Flink State Backend** | 流处理 | 状态存储 | Flink 窗口算子 |
| **ClickHouse** | OLAP 分析 | **改良版** MergeTree | 列式存储 + 向量化执行 |

**关键区分**：RocksDB 本身提供键值 API，而非分析查询。进行分析的系统要么：
1. 增加大量抽象层（Flink 状态管理）
2. 大幅修改存储格式（ClickHouse MergeTree 受 LSM 启发但不是 RocksDB）
3. 为简单性接受次优性能（早期原型）

### 选择 LSM Tree 当：
- ✅ 高吞吐键值写入（如缓存、会话、OLTP）
- ✅ 记录频繁小更新
- ✅ 每键强一致性要求
- ✅ 点查为主的负载（OLTP 模式）

### 选择 Lance 当：
- ✅ 向量/分析型工作负载（嵌入、特征存储）
- ✅ 批量导入，偶尔更新
- ✅ 需要列式投影和过滤
- ✅ 多模态数据（图像、视频与向量共存）
- ✅ ANN 搜索是主要查询模式

## 8. 总结

| 因素 | 胜者 | 理由 |
|------|------|------|
| **向量存储** | Lance | 列式页 + DV 避免重写放大 |
| **更新效率** | Lance | DV 标记 vs 完整记录重写 |
| **批量加载** | 平手 | 两者都针对顺序写优化 |
| **点查** | LSM | SSTable 布隆过滤器 + 层级跳过 |
| **ANN 搜索** | Lance | 原生 HNSW/IVF 配合稳定页引用 |
| **多模态** | Lance | 分层 blob 存储配合懒加载 |
| **运维简单性** | Lance | 更少调参，可预测的压缩 |

### 核心洞察

> **LSM Tree** 最初为**写密集型 OLTP**（替代 B-Tree）而发明，其核心设计保持行式和键值导向。
> 
> **Lance** 从一开始就专为**读密集型、列式 AI/分析**构建，避免了将 OLTP 存储适配分析工作负载的架构错配。

对于向量数据库，选择很明确：LSM 压缩在大向量数据上的开销超过其收益，而 Lance 的页式列式格式配合 Deletion Vector 为 AI 应用提供了写效率、读性能和存储经济性的最佳平衡。
